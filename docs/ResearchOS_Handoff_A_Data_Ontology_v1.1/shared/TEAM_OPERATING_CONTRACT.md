# 四人 Codex 团队操作合同

## 1. 共同规则

1. 先读 `AGENTS.md`、本角色 `00_START_HERE.md` 和 `shared/contracts/contract_manifest.json`；
2. 先做仓库盘点，不假设目录已经存在；
3. 只修改本角色拥有的目录；
4. 公共合同必须按 ICR 流程变更；
5. 每次 PR 必须说明生产者、消费者和合同影响；
6. 每个模块必须提供 Fixture；
7. 不允许直接耦合别人的数据库；
8. 不允许隐藏失败、模拟实时或伪造结果；
9. 功能冻结后只修 P0 Bug；
10. Codex 遇到越界请求时必须提醒人类并停止破坏性修改。

## 2. Codex 越界响应模板

当人类要求修改超出角色边界时，Codex必须回复：

> 该修改会改变冻结边界：`<合同/目录/状态>`。直接实施会影响 `<角色和模块>`，主要风险是 `<风险>`。  
> 我可以先提供一个不破坏合同的本地替代方案，或在 `docs/rfcs/` 生成 Interface Change Request。  
> 在 ICR 获得所需批准前，我不会修改共享合同或其他角色拥有的代码。

随后执行：

1. 列出受影响字段、端点和消费者；
2. 提供非破坏性方案；
3. 生成 ICR；
4. 保持代码不变；
5. 等待批准标记。

## 3. 完成定义

一个任务只有同时满足以下条件才算完成：

- 代码通过单元测试；
- 公共输出通过 Schema；
- Fixture 已更新；
- README 说明运行方式；
- 失败路径已测试；
- 未修改非本角色目录；
- PR 描述包含合同影响；
- 本角色验收清单全部打勾。

## 4. 每日/每轮状态格式

```text
Role:

Completed:

Need from other roles:
Next integration test:
```

## 5. 冲突处理

- 代码冲突由文件所有者解决；
- 合同冲突由 C 记录、全体裁决；
- 产品范围冲突以产品宪章为准；
- 统计方法冲突以 B 的注册模型和真实测试为准；
- 数据对象和版本冲突以 A 的对象身份规则为准；
- UI 不得通过隐藏字段规避后端冲突。
