# 研构 ResearchOS 产品说明书

> v1.1 大白话版  
> 给组员、PM、评委和第一次接触产品的人阅读

## 1. 我们在解决什么问题

现在每个人都可以用 AI 快速产生文件。一个四人小组很快会出现几十份：

- Markdown；
- Word；
- PDF；
- Excel；
- 代码说明；
- 数据表；
- 路演稿；
- 不同 Agent 的回答。

这些文件通常散落在微信群、个人电脑和不同聊天窗口里。团队随后要花大量时间找文件、问版本、复制内容和重新解释上下文。

研构提供一个统一项目面板。团队把文件批量投入后，系统保存原件，生成可理解的统一表示，再自动识别文件讲什么、属于哪个模块、由谁负责、和哪些文件有关、哪份是新版本，以及哪些内容互相冲突。

一句话：

> **把散落的文件变成会协作的研究资产。**

## 2. 数据本体用人话怎么理解

普通文件夹主要记录文件放在哪里。研构还记录：

- 文件是谁产生的；
- 它讨论哪个问题；
- 它属于草稿、候选还是正式决定；
- 它引用哪些文件；
- 哪份是它的新版本；
- 哪些内容和它冲突；
- 哪个 Agent 使用过它；
- 它更新后会影响哪些任务、模型和结论。

因此，一个 `.docx`、`.pdf` 或 `.md` 会成为有身份、有版本、有权限、有关系的研究对象。

## 3. 文件进入系统后会发生什么

### 3.1 保存原始文件

系统保留 Word、PDF、Excel 和 Markdown 原件，计算内容哈希，创建稳定对象 ID 和版本 ID。

### 3.2 生成规范化表示

```text
DOCX / PDF / Markdown
→ content.md
→ document.json
→ manifest.json

XLSX / CSV
→ table.csv 或 table.parquet
→ 字段目录
→ 单位、频率和缺失信息
```

### 3.3 AI 提出语义信息

AI 可以提出：

- 摘要；
- 标签；
- 模块；
- 决定；
- 未决问题；
- 接口；
- 负责人；
- 候选关系。

重要关系先进入候选状态。团队确认后才成为正式项目状态。

### 3.4 形成项目对象图

用户看到的内容包括：

```text
研构 ResearchOS
├── Research Ontology
├── Thesis Compiler
├── MacroTrace
├── Frontend
├── Deployment
└── Demo
```

每个模块下面挂着相关文件、版本、决定、接口、负责人和未决问题。

## 4. 它比本地文件夹强在哪里

文件夹能按路径保存文件。研构可以直接回答：

- 最新产品定义是哪一版；
- A 和 B 还有哪些接口未冻结；
- 哪些文件已经过期；
- 哪两份方案互相冲突；
- 某个修改会影响哪些 Codex；
- 给前端 Codex 应该提供哪些材料；
- 某个模型用了哪一版数据。

文件夹像储物柜。研构提供项目状态和关系。

## 5. 它比微信群强在哪里

群聊按时间排列。决定、闲聊和文件容易混在一起。研构把内容转成稳定对象：

```text
DECISION
OPEN_QUESTION
INTERFACE
TASK
RISK
FILE_VERSION
```

新成员可以直接读取项目当前状态，无需重翻全部消息。

## 6. 它比 Git 强在哪里

Git 擅长代码和文本差分。研构在此基础上增加：

- Word、PDF、Excel 的规范化；
- 文件语义；
- 跨文件关系；
- 项目决定和责任人；
- 权限和许可；
- 面向 Agent 的 Context Pack；
- 模型运行和结论影响。

普通用户只需看到“这是新版本、这些内容发生变化、这些任务受到影响”。

## 7. Context Pack 为什么重要

四个人分别使用自己的 Codex。每个 Codex 需要的材料不同：

```text
A 的 Codex：对象 Schema、文件处理、版本、关系和权限
B 的 Codex：MacroTrace、Data Resolve、ToolRequest 和 EvidenceBundle
C 的 Codex：ThesisBuild、编译规则、语言政策和版本差分
D 的 Codex：前端状态、OpenAPI、Fixtures、部署和 Demo
```

研构会为每个任务生成固定版本的 Context Pack。四个 Codex 使用同一套接口版本，减少“各自理解了一套产品”的问题。

## 8. 文件整理完之后，研究怎样真正运行

用户输入一条明确论点：

> 美国财政扩张正在持续推高 10 年期美债收益率。

系统先检查这句话：

- “财政扩张”如何定义；
- “持续”对应什么时间窗口；
- “推高”是否要求因果证据；
- 是否缺少货币条件、通胀和经济活动等竞争解释；
- 什么结果出现时应放弃该论点。

第一次构建会返回错误和验证计划。

随后 Thesis Compiler 调用 MacroTrace。MacroTrace 运行注册数据和模型，返回系数、置信区间、诊断、稳健性、Evidence Type 和局限。

## 9. 为什么 MacroTrace 不能直接决定最终结论

MacroTrace 回答：

> 注册数据和模型发现了什么。

Thesis Compiler 回答：

> 这些证据允许研究员把话说到什么程度。

例如，模型提供的是条件关联，原论点使用了独立因果措辞。系统会保留实证结果，同时阻止原因果论点通过，并生成更准确的降级表述。

最终状态包括：

```text
COMPILE_FAILED
EVIDENCE_INSUFFICIENT
SUPPORTED
WEAKENED
EVIDENCE_CONFLICT
```

## 10. 现场 Demo

### 第一段：共同研究状态

批量导入四位成员的项目文件。系统展示原文件、规范化表示、标签、版本、关系和冲突。

用户提问：

> A 和 B 之间还有哪些接口没有冻结？

答案可以回到具体文件和版本。

### 第二段：论点 Build Failed

输入待验证论点，系统显示定义、时间、因果和证伪错误。

### 第三段：调用 MacroTrace

验证计划生成 ToolRequest。Evidence Drawer 展示一个主模型、一个关键诊断和一个挑战结果。

### 第四段：重新编译

系统显示原因果措辞未通过，降级关联论点得到当前支持或证据不足状态。

### 第五段：版本差分

加入新数据或修订文件。系统只重算受影响模型和结论，其他节点继续复用。

## 11. 四个人分别做什么

| 人员 | 负责内容 |
|---|---|
| A | 文件对象、规范化、版本、关系、Context Pack 和 Data Resolve |
| B | MacroTrace、真实模型、诊断、EvidenceBundle 和离线快照 |
| C | Thesis Compiler、编译规则、工具编排、语言边界和最终状态 |
| D | 前端、部署、E2E、二维码、Demo Reset 和录屏 |

## 12. 产品边界

黑客松版本集中完成一条真实闭环：

```text
文件进入
→ 项目本体
→ 论点编译失败
→ 调用 MacroTrace
→ Evidence Bundle
→ 重新编译
→ 版本差分
```

本轮不追求完整企业权限、完整中国宏观迁移、任意模型代码生成、个股涨跌预测和无限并发。

## 13. 对外介绍

### 20 秒版本

> 研构把团队产生的 Word、PDF、Markdown 和 Excel 变成有版本、有关系的研究对象。研究员提出论点后，系统先检查证据缺口，再调用 MacroTrace 运行真实模型，最后决定现有证据允许结论说到什么程度。

### 结束语

> **让团队和 Agent 共享同一份研究状态，让每条结论都能回到文件、数据和模型。**
